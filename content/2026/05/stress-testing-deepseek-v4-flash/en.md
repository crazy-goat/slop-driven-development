## The problem with prompt-based workflows

For a while I tried automating my LLM tooling by writing workflows as markdown files inside repos. It caused more problems than it solved — thousands of skill and command MD files clogging the context window, the model randomly invoking them at wrong points in the workflow instead of where they were actually needed. And the data from this experiment makes it painfully clear why that approach doesn't scale: look at the tool usage chart from this test session — 38% of all tool calls are bash commands. That's git operations, running tests, running lint, creating PRs on GitLab. These commands are always identical for every task. They don't require intelligence, yet the LLM frequently gets them wrong. Worse, every bash call eats context that the model could be using to actually write code.

![Tool usage chart](/img/tool-usage-chart.png)

### Experiment costs

And there's another problem that compounds this. From my experience, current models lose context and break workflows on longer tasks. You tell them "never push to main branch" — and 50 messages later, they do exactly that because the instruction got buried or forgotten somewhere along the way.

The more I ran into these failures, the clearer it became: relying on prompts to enforce workflow rules is fundamentally fragile. Instructions degrade, context windows fill up, and the model improvises. Instead of fighting this, what if we took the workflow out of the conversation entirely? A YAML-based approach treats workflow as code — deterministic, version-controlled, reviewable. The LLM never needs to remember "don't push to main" because the workflow simply won't let it.

### The experiment:

This test was about establishing a baseline. If you write your entire workflow as LLM prompts — covering lint, tests, docs, CI/CD on GitHub, code review, issue handling, PR management — the Pareto rule applies: ~80% of the time it works fine. The system prompt plus task prompt in opencode takes about 25k tokens, and once that context is loaded, pipelines generally pass.

But that last 20% is painful. Case in point: if your repo uses "master" as the default branch and the LLM insists on "main" — it takes about 8 wasted tool calls before the model catches on. Eight tool calls just to figure out a branch name. That's 8 round trips of context consumption, each one eating tokens and time, for something that a script could handle in zero.

To find out exactly where models fail most often, I prepared ~100 real programming tasks across 4 different repos — different programming languages (PHP, C/C++, Go), different branch naming conventions (main vs master), different CI configurations. Every task was generated by GLM-5.1 from actual code analysis reports (code smells, security issues, missing tests, memory leaks) and then executed through deepseek v4 flash via opencode-go. The goal: push the model to its limits and map every weak spot.

![Different tool usage across sessions](/img/different-tool-usage.png)

### Different tool usage across sessions

I gave the LLM every advantage. Each repo had an AGENTS.md file with clear rules. A memory system called mind was available to persist important context across sessions — so the model could remember what it learned last time. None of it helped. The same mistakes kept happening, over and over:

- Attempting to push directly to the default branch without a PR
- Trying to close PRs that hadn't passed CI yet — and when CI blocked it, the model tried --admin flags to force it through
- Not closing issues after finishing work, which caused it to start working on the same issue again in a new session

Things get even worse when you add lint and static analysis to the mix. Tell the model to run the linter and it often simply won't — or worse, it will claim the errors were pre-existing and move on. The only reliable solution is to enforce linting via git hooks. That way you catch issues before commit, skip the CI waiting game entirely, and iterate faster.

And even when the model does run the linter, it's painful to watch. Despite a clear instruction in AGENTS.md that you can use the auto-fix flag, the model insists on manually fixing spaces, commas, and formatting by itself — sometimes making 20+ tool calls to fix a single file instead of running one command.

These mistakes make it clear: the LLM is not the right tool for workflow orchestration. But the whole point of this experiment was to find out exactly which parts of the pipeline NEED to be moved to deterministic tooling — and which can safely stay with the model. The answer, as the data shows, is most of the mechanical steps: branching, linting, testing, pushing, PR creation, issue management.

### The numbers:

I deliberately chose a "weaker" model for this experiment — cheap and fast, but more prone to mistakes. The idea: if it fails somewhere, that's a genuine weak spot that better models would likely hit too, just less often. And since cheaper models are faster, I could run more iterations and map the failure surface more completely. That's why deepseek v4 flash was the right choice.

Don't mistake "weak model" for "easy tasks." The issues ranged from trivial one-line fixes to complex multi-file refactors touching 106 files in a single session. Every issue was generated from real code analysis reports — code smells, security vulnerabilities, missing documentation, missing tests, performance issues, memory leaks — across 4 different repos in PHP, C/C++, and Go. Before starting work, each task was validated to confirm it was legitimate, and when multiple solution approaches existed, the best one was selected. Each task had to end with unit and functional tests passing, a changelog entry, and an updated docs section if default settings changed. Every issue had acceptance criteria. Every MR went through code review and had to fix all errors before merging.

Below are the overall results from the experiment run:

- 134 sessions (131 active) across 4 repos
- 4,600 messages exchanged
- 8.5M input tokens, 1.45M output + 930K reasoning tokens = 2.4M total output
- 395.5M cache read tokens (deepseek only)
- 7,498 tool calls
- Total cost: $2.97 (deepseek only)
- Duration: ~3 hours for actual coding work

**Per‑session metrics (59 build sessions):**

- Average: 92K input, 17K output, 15 min, 86 tool calls, $0.038
- Fastest: 0.2 min, 2 tool calls — read the issue, checked the code, determined it was already implemented elsewhere, moved on
- Longest: 35 min, 204 tool calls
- Most expensive single session: $0.121

**Code produced:**

- +23,505 lines added, −12,503 removed, 412 files touched
- Per build session (avg): +398 lines, −212 lines, 7 files
- Single‑session max: +6,338, −6,680, 106 files
- Sessions with extreme line counts were typically documentation cleanup or issue validation — issues started as markdown files in the repo, then the LLM validated, refined, and migrated them to GitHub issues

### What would this cost on other models?

If I ran the same workload through Sonnet 4.6, Kimi K2.6, or Opus 4.7 on OpenRouter, here's what the math looks like — including full cache lifecycle (write + read) for Anthropic models:

| Model | Estimated cost | vs deepseek |
|---|---|---|
| deepseek v4 flash | **$2.97** (actual) | 1× |
| Kimi K2.6 | ~$161 | 54× |
| Sonnet 4.6 | ~$1,663 | 560× |
| Opus 4.7 | ~$2,772 | 933× |

Now someone will inevitably say "but Sonnet and Opus are SOTA — they'd burn way fewer tokens because they think better." No, they wouldn't. I ran comparison tests on several tasks and the token consumption was essentially the same. Here's why: the tasks were well-described with clear instructions on what to implement and where. The LLM didn't need to think — it needed to write code, add tests, update docs, and handle lint fixes. Most tokens were burned on workflow operations and repetitive lint/static analysis corrections, not on reasoning. A smarter model doesn't use fewer tool calls to run git push or fix a missing space.

### What I learned:

- **Speed matters more than you think.** What I expected to take several evenings was done in 3 hours. Deepseek v4 flash generates code so fast that the bottleneck shifts entirely to your tooling and review process.
- **Code quality surprised me.** Good enough that I'm reconsidering my default model choice. I originally planned to use Kimi or Sonnet for production — now deepseek v4 flash is a serious contender for daily use.
- **The markdown workflow approach failed**, and that's exactly the point. I had to manually fix things during the test. But that's why I ran this experiment — to break the markdown-based workflow and find the weak spots before moving to a proper state machine.

After this experiment I realized I needed a better approach. I looked for existing tools and found Dagu — it looked promising, so I gave it a try. It's a solid tool, but after experimenting I realized something was still missing. Dagu's DAG model couldn't express the transitions, conditional branching, and retry logic I needed — it's not a full state machine. So I decided to use deepseek v4 flash to vibe-code my own YAML-based workflow tool where deterministic steps (create branch, lint, test, push, create PR) are handled by shell scripts, not by a model guessing the right git flags for the hundredth time. Let the LLM focus on what it does best: writing code.

### What's next:

1. Write my own YAML-based workflow tool
2. Compare token usage: YAML workflow tool vs. all-in-LLM approach — measuring both speed and cost
3. Migrate from opencode-go to a lighter alternative — current overhead is ~20k tokens per session start just for the system prompt

### Final thoughts

Building reliable agentic coding systems is still an open problem — and I'm at the very beginning of what promises to be an epic journey. My bet is that the sweet spot is using expensive models for planning and breaking down tasks, then handing the execution to cheap, fast models. Deepseek v4 flash proved it can handle the grunt work reliably and at a price point that makes this architecture viable — even with some token waste on workflow mistakes, the economics still work out compared to running everything on Sonnet or Opus.

Even a basic approach — wrapping the mechanical steps in shell scripts — showed immediate improvement in my initial tests. The model spent less time on git gymnastics and more time writing code. That's when I started looking for proper workflow tools and found Dagu. Early tests with Dagu pushed the improvement further, and I'm confident a purpose-built YAML state machine will go even further.

The biggest surprise — and the biggest winner — was deepseek v4 flash itself. I went into this experiment expecting most of its output to end up in the trash. After manually reviewing several changes and running Opus over the rest, the verdict was clear: **most of the code was solid. Some of it was genuinely good.** A $2.97 model producing production-quality code across 4 languages and 400+ files. That changes what I thought was possible.
